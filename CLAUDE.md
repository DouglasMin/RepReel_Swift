# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An iOS app that turns Instagram Reels workout videos into structured, trackable
training programs. A Reel is shared into the app, an AWS backend runs AI
extraction, and the app renders the resulting hierarchical program and logs
sessions against it.

The backend is **not** in this repo. `docs/` is the contract:

| File | Role |
| --- | --- |
| `docs/API_SPECIFICATION.md` | Authoritative REST contract — 15 endpoints, headers, JSON shapes |
| `docs/SWIFT_MODELS.swift` | Reference domain models, ported into `ReelsKit/Sources/ReelsKit/Models/` |
| `docs/IOS_SHARE_EXTENSION_GUIDE.md` | Original share-extension outline; the shipped version is refactored onto ReelsKit |

`docs/SWIFT_MODELS.swift` is reference material only — it is **not** compiled and
is not a target member. Edit the ported copies under `ReelsKit`.

## Commands

```bash
make bootstrap    # first run: copies Secrets template, generates the Xcode project
make generate     # regenerate ReelsWorkout.xcodeproj — REQUIRED after adding/moving/deleting any file
make unit         # fast loop: ReelsKit tests only, no simulator (~1s)
make build        # build app + extension for the simulator
make test         # full xcodebuild test run
```

Single test:

```bash
cd ReelsKit && swift test --filter "Round-trips a session log"        # by test name
cd ReelsKit && swift test --filter "APIClient"                        # by suite
xcodebuild test -project ReelsWorkout.xcodeproj -scheme ReelsWorkout \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro' \
  -only-testing:ReelsWorkoutTests/LibraryStoreTests CODE_SIGNING_ALLOWED=NO
```

Run it:

```bash
xcrun simctl boot "iPhone 17 Pro"
xcrun simctl install "iPhone 17 Pro" \
  ~/Library/Developer/Xcode/DerivedData/ReelsWorkout-*/Build/Products/Debug-iphonesimulator/ReelsWorkout.app
xcrun simctl launch "iPhone 17 Pro" "$(grep '^APP_BUNDLE_ID' Config/Secrets.xcconfig | cut -d= -f2 | xargs)"
```

## Project generation

`ReelsWorkout.xcodeproj` is **generated by XcodeGen from `project.yml` and is
gitignored**. Never hand-edit the `.pbxproj`; edit `project.yml` and run
`make generate`. Targets pick up sources by directory, so a new `.swift` file
inside `ReelsWorkout/`, `ReelsShareExtension/`, or `ReelsWorkoutTests/` joins its
target automatically after regeneration — but a build against a stale project
will simply not see the file.

## Architecture

Three build products, one shared library:

```
ReelsWorkout (app)  ─┐
                     ├─→ ReelsKit (local SPM package: models, APIClient, config, App Group stores)
ReelsShareExtension ─┘
```

**`ReelsKit` must stay free of UIKit and SwiftUI.** It declares a macOS platform
purely so `swift test` runs on the command line without booting a simulator;
importing a UI framework breaks that fast loop.

### Data flow

1. **Share extension** (`ShareViewController`) pulls the Reel URL out of the
   `NSExtensionItem` (Instagram sends a URL attachment, sometimes plain text with
   an embedded link — both paths are handled), calls `POST /reels`, appends a
   `PendingJob` to the App Group, and dismisses. It has a few hundred ms to live:
   keep work here minimal and never block on analysis.
2. **App** reads those jobs on `scenePhase == .active` (`LibraryView`), because
   the extension writes while the app is backgrounded. `LibraryStore` spawns one
   poll task per job against `GET /jobs/{id}`, and on `COMPLETED` removes the job
   and reloads `GET /programs`.
3. **`ProgramDetailView`** renders the Program → Day → ExerciseGroup → Exercise
   hierarchy from `GET /programs/{id}`.

`AppEnvironment` is the single composition root (`@MainActor @Observable`),
injected via `.environment(_:)`. Feature stores (`LibraryStore`) are
`@MainActor @Observable` classes constructed with an `APIClient` — never with a
global.

### Auth

Every request carries `x-app-secret` + `x-user-email`; the backend 403s on a
missing/unknown pair before spending any compute, so `APIError.forbidden` means
"allow-list or secret", not "session expired". `APIClient` reads the email
through a `@Sendable` closure so signing in mid-session does not require
rebuilding the client. Sign in with Apple is **not implemented yet** —
`UserIdentityStore` holds the email in the App Group, seeded from
`DEV_USER_EMAIL`, and both processes read it from there.

### Testing seam

`APIClient` takes an `HTTPTransport`; inject a stub instead of hitting the
network. See `ReelsKitTests/APIClientTests.swift` (header/URL assertions) and
`ReelsWorkoutTests/LibraryStoreTests.swift` (suffix-matched route table).

## Configuration

`Config/Base.xcconfig` holds committed defaults and `#include?`s
`Config/Secrets.xcconfig` (gitignored) at the bottom so local values win. Both
feed target Info.plists, which `AppConfig.fromBundle()` reads at launch. The app
and the extension each read their **own** `Bundle.main`, which is why both
Info.plists carry the same five keys.

Two gotchas that will bite:

- **`//` starts a comment in xcconfig.** That is why the config stores
  `API_HOST` (host only) and `AppConfig.baseURL` re-adds the `https://` scheme.
  Do not try to store a full URL there.
- **Manual Info.plists need explicit bundle identity.** `GENERATE_INFOPLIST_FILE`
  is off, so `CFBundleIdentifier`/`CFBundleExecutable`/`CFBundlePackageType` must
  stay spelled out as `$(...)` in each plist. Dropping them still *builds* but
  fails at install with "Missing bundle ID".

A misconfigured build shows `ConfigurationErrorView` instead of 403ing on every
request — `AppConfig.fromBundle()` rejects values containing `REPLACE_ME`.

## Deliberate deviations from `docs/`

Keep these in mind before "fixing" a model to match the docs:

- **Most scalar fields are optional.** `docs/SWIFT_MODELS.swift` declares them
  non-optional, but the response examples in `API_SPECIFICATION.md` omit them —
  e.g. `program_data` carries only `days`/`progression`/`audit`, while the
  wrapper carries `title`/`split_type`. Read display values off
  `WorkoutProgramResponse`, not off the nested `WorkoutProgram`.
- **`ProgramSummary`** exists because `GET /programs` rows have no
  `program_data` and will not decode as `WorkoutProgramResponse`.
- **`ExerciseGroup.id`** folds in the first exercise id. Category + region alone
  can repeat within a day, and duplicate ids corrupt `ForEach`.
- **The App Group stores JSON `PendingJob` records** under `pending_jobs`, not
  the plain `pending_job_ids` string array from the share-extension guide, so the
  app can show *which* reel is being analysed.
- **`GET /sessions/active` answers 404 when there is simply no draft**, with a
  `{"has_active_session": false}` body. That is the ordinary "nothing in
  progress" case, not a failure — it must not surface as `APIError.notFound`.

## Live workout sessions

The backend keeps a **server-side draft** of the workout in progress, so a
checklist survives the app being killed mid-gym:

| Endpoint | When |
| --- | --- |
| `PUT /sessions/active` | Every set checked / weight edited — fire-and-forget in the background |
| `GET /sessions/active` | App launch, to offer "you have an unfinished workout, resume?" |
| `DELETE /sessions/active` | User discards the workout |
| `POST /sessions` | "Finish workout" — server computes volume and clears the draft |

There is one draft per user (keyed on `x-user-email`), not per program.

`volume_analytics` (total tonnage, sets, reps, per-exercise 1RM estimate) is
**computed server-side** on both the draft and the finished session. Do not
recompute it on the client for display; `LoggedSet.setVolumeKg` exists only for
optimistic UI between saves.

next-session overload, coach Q&A, exercise substitution, and the whole live

endpoints. Sign in with Apple and the app icon are also outstanding.
